## [Unreleased]

### Added

- The reporter writes a job summary on the workflow run's page, for every event: its PR comment (the summary line, the ZIP or report link, the changed, new and missing snapshots with their hints) without the hidden markers and the `/testivai approve` commands (the code blocks and the approve-all line), since nobody can comment from a run page. It is written before the comment is posted, so a token that cannot comment (a fork's pull request, no `pull-requests: write`) still leaves it. A push to the default branch, which has no comment, now shows its result there. It is built from the comment's own markdown (`summaryFromComment`), so the two cannot drift. A summary that cannot be written only warns
- `publish@v1`: a job summary says what the publish did: the site's address, the default branch's latest run and each open pull request's (links, counts, a fork tagged), and the runs left out and why, from the same data as the site's front page. When nothing is published, the reason, with what an admin can change, is on the run page and not only in the log. A fork's title, and why its report could not be shown, are left out (numbers and links only, as in the bot's comment on a fork); other text is escaped. The finish step writes it after the deploy and the comments, the build step when nothing is published; a summary that cannot be written only warns
- `publish@v1` publishes each changed snapshot's thumbnail (`thumb.png`, written by `@testivai/witness` 2.6.0 and later: the changed area of the baseline, the current capture and the diff side by side, at most 800×400 px) at `images/<n>/thumb.png` beside the run's other images, after the same PNG header check and only within the 800×400 px a thumbnail can be; one that fails either is left out and named on the page like any other image. The report page itself does not show it
- The PR comment shows each changed snapshot's thumbnail once `publish@v1` has published it: the first line inside the snapshot's `<details>` is the picture (baseline | current | diff of the changed area), linked to the snapshot's card in the report, for the first 5 changed snapshots that have one, and the first 3 of those are expanded (`<details open>`) so it shows without a click. It comes with the publish's edit of the comment, like the report links; without a published report the comment is unchanged. Only an https URL inside the run's report URL is used, and the snapshot name in `alt` is escaped. A private Pages site gets no pictures (GitHub fetches a comment's images without the reader's sign-in, so they would show broken), and a fork's pull request gets none either: the reporter's comment rebuilt there (a `pull_request_target` run can comment) has the links but no pictures, as the fork's run chose them, and the comment the publish posts on a fork's pull request stays numbers and links only
- The PR comment reads capture health from `results.json` (`@testivai/witness` schema 2.7.0 `captureHealth`): when a web font or stylesheet failed to load in the current capture or the baseline, the snapshot reads **Unhealthy capture** with what failed, in plain words ("web font 'Fancy' failed to load, so the page rendered with a fallback font", "stylesheet example.com/css/site.css returned 404"), before any environment reading and never as "likely render noise"; an unhealthy baseline reads "the baseline was captured with a failed stylesheet (…). Re-baseline from a healthy run." on every compare against it. A passed snapshot with an unhealthy capture gets a line of its own, a new one says so on its line ("do not approve it as the baseline"), and broken images and failed scripts are shown as **Capture warnings** without changing the reading. Results without `captureHealth`, or with healthy captures on both sides, give the same comment as before
- `approve@v1`: the reply names each approved capture that was unhealthy, from its `metadata.json` in the downloaded report, and says to re-run and approve a healthy capture
- `review@v1`: the triage rubric (bundled in `dist/review.cjs`) gets a row for unhealthy captures: a glitch of the capture or a broken asset, never approved as a baseline; a bug when the change under test touched the asset that failed
- The PR comment reads `captureHealth.sameOnBothSides` (`@testivai/witness` schema 2.8.0): when the baseline and the current capture failed in exactly the same way (a font or stylesheet broken on every run), the **Unhealthy capture** line says "the baseline was captured with the same failures" and that the pass tolerances (`maxDiffPercent`, `maxDiffPixels`, `shiftTolerance`) still apply but noise auto-pass does not; a passed snapshot's line names the criterion that passed it ("auto-passed by the 'threshold' criterion"). `review@v1`'s triage rubric says the same diff compares like with like
- `publish@v1` keeps `captureHealth.sameOnBothSides` from a report (only `true`, only with `unhealthy: "both"`)
- `publish@v1` can publish next to a website: new inputs `site-dir` (an already-built site, deployed at the root as it is) and `reports-path` (the folder the reports go in, such as `visual-reports`), for a repository whose Pages site is a website or docs. Everything the action makes goes under `reports-path`: the reports' front page, `pr/<number>/…`, `main/`, the links in pull request comments and the approve reply, and the `page-url` output. No site file is ever written over: a site that already has `reports-path` fails the publish before anything is read from GitHub, and every file is created only if it does not exist. Symbolic links in the site are skipped and its size counts toward the 900 MB budget (reports go first, never the site); hidden files are uploaded with it (`include-hidden-files`, only with `site-dir`); only report pages get `noindex`; no `404.html` is written (the site's own is served). Where the settings refuse the reports but allow a deploy (a private repository's public site without `TESTIVAI_PUBLIC_REPORTS`, or a custom domain without Enforce HTTPS), the site is deployed without them: no report is downloaded, nothing goes under `reports-path`, no comment is touched, and the new `reports-published` output says `false`. Where Pages is off or builds from a branch, nothing is deployed and the branch keeps serving the site. Build `site-dir` from the default branch, never from a pull request: setup in [A website at the root, reports under a path](../docs/github-action.md#a-website-at-the-root-reports-under-a-path). Without the new inputs, nothing changes

### Changed

- `publish@v1` downloads only the reports it has not built before; the rest come from the Actions cache. A run's report never changes (a re-run uploads a new artifact), so each report ZIP a publish downloads is kept as `<artifact id>.zip` in `$RUNNER_TEMP/testivai-pages/cache`, which `actions/cache/restore@v6` restores before the build and `actions/cache/save@v6` saves right after it, under a key per run (`testivai-pages-reports-v1-<repository id>-<run id>-<attempt>`, restored by its prefix, so the newest comes back). A publish that added or removed no report saves nothing, and a report no longer published leaves the cache with the next publish. Nothing from the cache is trusted: a ZIP is used only when its SHA-256 is the digest GitHub lists for the artifact (anything else is downloaded again; an artifact without a digest is never kept), and every page is still rebuilt from it with the same checks as a download, so the site is byte for byte what a publish without the cache builds. A cache that cannot be restored or saved never fails the publish. The job log says how many reports were downloaded (and how many MB) and how many came from the cache. New input `cache`, off by default (`cache: true` turns it on): `actions/cache` unpacks an entry before the action checks it, in a job that holds `pages: write` and `id-token: write`, and a default-branch workflow with a writable cache (push, schedule, `workflow_dispatch`) can save one, so turn it on only where no code you do not trust runs in such a workflow; off, every publish downloads every report, as before. Each publish that changes the set of reports saves a new full copy of the folder (up to the site's 900 MB budget), and old copies go only when GitHub evicts them (unused for 7 days, or least recently used once the repository is over its cache limit), so on a busy repository it can push out other caches. No new permissions.

## [1.5.0] - 2026-10-19

### Added

- `approve@v1`: the reply to `/testivai approve` names the CI run whose captures were approved (`from CI run 123, attempt 2`, linked). When `publish@v1` has put that run's report on GitHub Pages, the reply also links it (**Open the visual report**) and each approved snapshot's card in it (`open in report`, the same `#snap-<name>` anchors as the PR comment). The link is never guessed: it is taken from a github-actions[bot] comment whose run marker names the approved run, and only when it points at that run's page on that pull request; the run is the one the report was downloaded from, with the attempt from the report's run stamp when the stamp names that same run. If the comments cannot be read, the reply goes without the link. The reply step now loads `action/dist/approve.cjs`, which ships with the action at the same tag; no new permissions are needed

## [1.4.1] - 2026-10-19

### Fixed

- `publish@v1`: a pull request opened from a branch name an earlier pull request used no longer lists the earlier one's runs on its page of the site. A pull request's runs are now the ones on its branch since it was opened; GitHub's own run list attributes the earlier runs to the open pull request too. Seen on testivai/testivai-example, where #17 reused #16's branch and its page showed #16's trial runs
- `publish@v1`: the `page-url` output (and so the `github-pages` environment's link, when the workflow sets `url` from it) is the site's https address. It passed on deploy-pages' `page_url`, which GitHub gives as `http://` for a github.io site; the comments already linked https

## [1.4.0] - 2026-10-18

### Added

- The PR comment can link straight into a published copy of the HTML report: **Open the visual report** above the snapshot list (the ZIP download stays beside it), and an *open in report* link on each changed snapshot's row and each new snapshot that lands on its card (`#snap-<name>`, the same id the report gives it). Only an https URL that cannot break out of the link is used. The links appear when the report is published for the run; without one the comment is unchanged
- The comment records which CI run it describes in a hidden `<!-- testivai-run:<run id>-<attempt> -->` marker, so a later update (such as publishing the report) can check the comment is still about that run before changing it
- `testivai/testivai-oss/publish@v1` publishes reports to the repository's GitHub Pages site, so the comment links the report instead of a ZIP: the last 3 runs of each open pull request (forks included) at `pr/<number>/<run id>-<attempt>/`, the default branch's latest run at `main/`, a front page, a page per pull request and a 404 page for a report no longer published. The site is rebuilt from scratch on each publish, so a closed pull request's reports go with the next one; it replaces the repository's whole Pages site. It publishes only where an admin set Pages to "GitHub Actions"; a private or internal repository's reports go on a public site only with `TESTIVAI_PUBLIC_REPORTS=true`. A page is never the artifact's own HTML: it is rebuilt from `results.json` as `parseReportData` checks it and from the PNGs that pass a header check (at numbered paths), the ZIP is inflated in slices with caps, and every page is noindex under a content security policy. After the deploy it adds the links to the TestivAI comment when its run marker names the published run, and posts a comment of its own (numbers and links only) on a fork's pull request, whose run cannot comment. It never checks out or runs the pull request's code. Pages of your own (a demo, a landing page), built by an earlier step from the repository's own code, can go on the same site with `include-dir` and `include-name`. Setup: [Reports on GitHub Pages](../docs/github-action.md#reports-on-github-pages)
### Changed
- The PR comment reads capture provenance from `results.json` (`@testivai/witness` schema 2.5.0): when the baseline and the current capture both recorded their environment and the rendering environment changed (a browser build, OS or distro, device scale, capture method), a diff with an identical DOM and matching styles reads **Rendering drift** with the change named ("chromium 130.0.6723.58 → 141.0.7390.37"), never "likely render noise"; a size change from another capture method reads **Capture method changed**; a snapshot that `environmentPolicy: "strict"` made changed says so; any other reading keeps its line and mentions the environment change as context. When two or more snapshots share one change, the comment says it once at the top with an honest count of how many are drift. The review action's triage rubric (bundled in `dist/review.cjs`) gets a row for rendering drift: a glitch of the environment, or an intended change when the change under test upgraded the environment; re-baseline either way

### Fixed

- A missing baseline no longer lets a changed snapshot through the gate. When a run had both, the check run reported `neutral` ("N baselines received no capture") and the commit status `success`, and the job passed, even with `fail-on-diff: true`: a pull request that dropped or renamed one snapshot while breaking another got past a required `TestivAI / visual` check. A changed snapshot now fails the check whenever `fail-on-diff` is set, with or without missing baselines; `fail-on-missing` still decides the missing baselines on their own. Missing baselines still lead the check's title and summary, which now also count the changed and new snapshots of the same run; a failing check's summary opens with what failed it ("Fails the check: 2 snapshots changed."), and its title ends "— visual regression" when changes fail it. This matches the CLI's exit codes, which rank changed above missing. `fail-on-missing` is now listed in the Inputs tables of the docs and the action README
- A taller or shorter capture no longer reads as "content was added below the baseline's height" in the PR comment: the padded band at the bottom is the page's new height, not where the change is. The **Size changed** line now uses the same reading as the report and the MCP verdicts (`explainHeightChange` from `@testivai/witness`): a page shift places the change ("everything below y=203 moved down 73 px, so look above that line"; the separate **Layout shift** line is then not repeated), a DOM change says what changed but not where, and an identical DOM is the same content laid out taller or shorter (restyled, or often fonts or rendering that differ between machines), never content added or removed

## [1.3.0] - 2026-10-17

### Changed
- The PR comment reads `sizeMismatch` from `results.json` (`@testivai/witness` schema 2.4.0): when the current capture's dimensions differ from the baseline's, the snapshot row shows both sizes (`baseline 1280×2348 → current 1280×2538 (+190 px)`) and the body opens with **Size changed**: a taller or shorter page is content added or removed, read with the DOM summary; a width change is the viewport or device scale, not the page. The identical-DOM readings (likely render noise, styles not compared) are withheld for such a snapshot, because its diff is on a padded canvas in which every padded pixel counts as changed (#197)

## [1.2.0] - 2026-10-16

### Changed
- `testivai/testivai-oss/review@v1` triages missing baselines too: committed baselines that got no capture this run (`missingBaselines` in `results.json`), because their test was removed, renamed or skipped, or failed before it captured. A push whose only finding is a missing baseline now starts a run instead of skipping with "nothing to triage". The prompt lists missing baselines apart from the changed and new snapshots (one cap of 30 names across both) and says where each one's committed baseline is (`baselinesDir` in `.testivai/config.json`, `{platform}` included, else `.testivai/baselines`), so Claude can read its `screenshot.png` even with an older `@testivai/mcp`. The shared rubric judges one by the change under test: an intended removal or rename, a bug (an unintended one, or a change that broke the test before its capture), otherwise a possible bug with a pointer to the test run's log; never a glitch. The comment marks those rows `(missing)`, counts them in the tally, and says that approving does nothing for them: an intended removal deletes the baseline directory. With `failOnMissing: false` in `.testivai/config.json` (missing baselines are expected, as in a `--grep` run or one browser lane of a matrix) they are left out, so they never start a run on their own (#193)

## [1.1.1] - 2026-10-16

### Changed
- `testivai/testivai-oss@v1` runs on Node 24 (`runs.using: node24`, dist built for node24), and `approve@v1` and `review@v1` run their scripts on `actions/github-script@v9` (`approve@v1` checks out with `actions/checkout@v7`) instead of releases that target Node 20, which GitHub's runners deprecate. ## [1.1.0] - 2026-10-16

### Added
- `testivai/testivai-oss/review@v1` (`review/action.yml`): on a pull request with a changed or new snapshot, Claude (`anthropics/claude-code-action`) triages each one as a glitch, an intended change, a bug or a possible bug, using the TestivAI MCP server, the images and the pull request's diff, and posts one comment updated on each push. It uses the MCP server's `triage-visual-diff` rubric, bundled as `dist/review.cjs`. Advisory: it never changes the visual check or a baseline, and Claude gets read-only tools. It skips without using tokens when `enabled: false`, when nothing changed, on non-PR events, without a Claude credential (`anthropic-api-key` or `claude-code-oauth-token`), or for a bot not in `allowed-bots`; `model` and `max-turns` bound the cost. Claude reads only inside the workspace (not `.git`, `/proc` or `/sys`) and gets the job's own `github.token`; its answer is posted with secrets redacted and HTML, mentions, links and images defanged, within GitHub's comment size limit. A run superseded by a newer push never writes the comment, and a comment that cannot be written is a warning, not a failed job

### Changed
- The PR comment calls an identical-DOM diff with matching computed styles "likely render noise" only when the diff is small and scattered. When every diff region fits in a box covering at most a third of the page, it says **DOM and styles unchanged, but the diff is concentrated in one area**, names the regions and their box, and says it is a bad capture or a change the style check does not cover (size, overflow, transform, images…); a spread-out diff over 1% of pixels says **the diff is large**. Both ask for the images to be compared before approving. The rule is `diffShape` from `@testivai/witness`, read from `results.json` fields older witness versions already write

## [1.0.10] - 2026-07-14

### Added
- `status-context` input to customize the commit status context (default `TestivAI / visual`), so repos with multiple visual lanes (e.g. Playwright + pytest) can post separate statuses instead of overwriting each other. A non-default context also namespaces the PR comment upsert marker, giving each lane its own comment; the default context keeps the legacy marker so existing PR comments continue to update in place

"@testivai/mcp": patch

A capture whose dimensions differ from its baseline's is now always reported as changed. `compareAll` sized the diff canvas to the baseline and truncated the candidate to it, so a page that grew (content added below the fold) had an identical overlap, `diffCount: 0`, and was passed at 0% while the DOM diff said elements were added; a different width misaligned every row into a nonsense diff. The two captures are now padded to the larger width and height, every padded pixel counts as changed and is painted as heat in the diff image (the engine's `diff()` takes the new `dimensions` option for that, so a width difference normalizes too; with `handleSizeMismatch: 'pad'` the engine now counts the padded pixels in `diffCount` on its older length-inferred path as well), and the result records both sizes as `sizeMismatch` (results.json schema 2.4.0, additive). No pass criterion (`maxDiffPercent`, `maxDiffPixels`, `noiseAutoPass`, `shiftTolerance`, or the zero-count pass) applies to a snapshot with `sizeMismatch`; a byte-identical capture still takes the fast path, and a DOM change on its own still never decides the status (the pixel tolerances stay pixel tolerances). A passed snapshot whose DOM changed, with nothing visible or within a tolerance, now says so in the report and the MCP verdict and guidance instead of asking to confirm before approving. The report row shows both sizes (`baseline 1280×2348 → current 1280×2538 (+190 px)`), and the verdict says what the change means: a taller or shorter page is content added or removed, with the DOM summary; a width change is almost always the viewport or device scale factor, not the page. `@testivai/witness/report` exports the shared wording (`describeSizeChange`, `formatSizeMismatch`, `formatSizes`, `sizeMismatchKind`). In `@testivai/mcp`, `get_visual_results` gives such a snapshot the size verdict before any other reading, `explain_snapshot` carries the two sizes in the pixel layer and leads its guidance with them, and a snapshot whose dimensions changed is never grouped with others, since its pixel signals describe the padding.
